# Detection Engine Overview & Operational Guide

The **Detection Engine** (`src/modules/detection/`) is an autonomous background analysis module built into the Pipeline Leak Detection System backend. It monitors pipeline telemetry data generated by field sensors and automatically identifies leak incidents using physical anomaly detection rules.

---

## 1. What the Detection Engine Does

Rather than relying on human operators to inspect raw sensor numbers or waiting for an API request, the Detection Engine runs automatically on a scheduled timer (e.g. every 10 seconds).

During each cycle, it:
1. Locates all defined pipeline **Segments** that have both a **Start Sensor** and an **End Sensor** installed.
2. Pulls the latest telemetry readings (pressure, flow rate, temperature) recorded by those sensors.
3. Evaluates physical fluid dynamic rules to determine if fluid is escaping from the pipe segment.
4. Automatically opens new **Leak Incidents** (with appropriate confidence levels) or auto-resolves existing incidents when physical conditions return to normal.

---

## 2. The Two-Signal Decision & False-Positive Guard

A single unusual sensor reading could be caused by electrical noise, temporary valve movement, or sensor recalibration. To prevent false alarms, the Detection Engine uses a **Two-Signal Verification Guard**.

### Signal 1: Pressure Drop Signal
- **What it checks:** Measures whether fluid pressure at the segment's **start sensor** has dropped below its recent baseline.
- **Threshold:** Default **15% drop**.
- **Sustained Duration Rule:** The drop must persist for **at least 3 consecutive readings**. A brief 1-tick dip is ignored.

### Signal 2: Flow Rate Mismatch Signal
- **What it checks:** Compares the fluid volume entering the segment (start sensor flow rate) against the fluid volume exiting the segment (end sensor flow rate).
- **Threshold:** Default **10% variance/mismatch**.
- **Sustained Duration Rule:** The mismatch between input and output flow must persist for **at least 3 consecutive readings**.

---

## 3. Confidence Scores & Decision Outcomes

When evaluating a segment, the engine decides between 5 outcomes:

| Outcome | Signal Conditions | Segment Status | Confidence | Action Taken |
| :--- | :--- | :--- | :--- | :--- |
| **High-Confidence Leak** | Both Pressure Drop ($\ge 15\%$) **AND** Flow Mismatch ($\ge 10\%$) agree for $\ge 3$ ticks | `LEAK` | **0.95 (95%)** | Opens `LeakIncident` with `status: OPEN`. Emits `incident.created` event. |
| **Low-Confidence Warning** | Pressure drop persists for an extended duration ($\ge 5$ ticks), but flow rate is unconfirmed | `WARNING` | **0.65 (65%)** | Opens `LeakIncident` with `status: OPEN`. Emits `incident.created` event. |
| **Incident Upgraded** | Existing `OPEN` incident was low-confidence (`0.65`), but flow mismatch signal now agrees | `LEAK` | Upgraded to **0.95** | Updates existing incident confidence to `0.95` and segment status to `LEAK`. Emits `incident.upgraded` event. |
| **Duplicate Skipped** | Anomaly detected, but segment already has an `OPEN` incident matching the current confidence tier | Unchanged | Unchanged | Logged as duplicate; no new record created. |
| **Auto-Resolved** | An active `OPEN` incident exists, but recent readings show pressure and flow have recovered to normal | `NORMAL` | N/A | Updates incident `status: RESOLVED` with `resolvedAt` timestamp. |

---

## 4. Automatic Incident Resolution

If a leak was fixed by field technicians or a simulated leak completes its duration, the system automatically recovers:
1. The engine checks active segments with an `OPEN` incident.
2. If both pressure drop and flow mismatch drop back within safe bounds (below 50% of threshold values), the engine marks the incident as `RESOLVED`.
3. The parent segment's status is flipped back to `NORMAL`.

---

## 5. Event Decoupling & Integration Architecture

The Detection Engine connects telemetry data with future alerting modules:

```
┌────────────────────────┐      ┌────────────────────────┐      ┌────────────────────────┐
│    Sensor Readings     │ ───► │    Detection Engine    │ ───► │    Alerting Module     │
│  (Ingested telemetry)  │      │ (Two-Signal Evaluation)│      │(Listens to event queue)│
└────────────────────────┘      └───────────┬────────────┘      └────────────────────────┘
                                            │
                                  Emits 'incident.created'
                                  Internal EventEmitter2
```

- **Upstream (Inputs):** Ingested telemetry from `POST /readings` stored in PostgreSQL.
- **Downstream (Outputs):** The Detection Engine does **not** send emails or SMS messages directly. Instead, when an incident is raised, it emits an internal event (`incident.created`).
- **Decoupled Alerting:** Future notification modules can subscribe to `incident.created` to dispatch SMS/Email alerts via background queues without slowing down the core detection cycle.

---

## 6. Environment Configuration Variables

The following variables in `.env` customize the engine's behavior:

```env
# Evaluation loop frequency in milliseconds
DETECTION_INTERVAL_MS=10000

# Number of recent readings evaluated per sensor
DETECTION_SAMPLE_SIZE=5

# Minimum percentage pressure drop required to trigger Signal 1
DETECTION_PRESSURE_DROP_THRESHOLD_PCT=15

# Maximum allowable flow percentage difference between start and end sensors
DETECTION_FLOW_MISMATCH_TOLERANCE_PCT=10

# Consecutive reading ticks required to validate a sustained signal
DETECTION_MIN_SUSTAINED_TICKS=3
```
